font-detector ・ 画像内の文字の判定方式

文書ごとのフォント分類器

PDFの本文には、どのフォントでどの字形が描かれているかが記録されています。これをそのまま正解付きの学習データにして、文書を開くたびに小さな分類器を学習し、画像の中の文字がどのフォントで書かれているかを判定します。

入力: PDFの本文 (正解付き) 書 書 MS 明朝 / 游ゴシック …
→
出力: 画像内の各行 どのフォントか ＋ 確率 PDFに無い書体は「その他」
scikit-learn ・ CPU のみ ・ オフライン 学習済みモデルのダウンロード不要 実装: src/font_detector/mlclassifier.py
なぜ機械学習か

同じ文字が本文に無くても判定できる

従来の字形照合は、画像内の文字を、本文にある同じ文字の字形と比べます。Word が埋め込むフォントは使った文字だけのサブセットなので、画像内の文字が本文に無ければ比べられません。評価では、PDFのフォントで書かれた行のうち判定できたのは 25% でした。

分類器が学習するのは文字の形そのものではなく、線の太さ・縦画と横画の太さの比・形の傾向といった書体の特徴です。そのため、学習に使っていない文字でも書体を判定できます。

処理の流れ

文書を開いてから判定まで

  1. 本文から字形を集める学習 PDFのフォントごとに、出現頻度の高い文字を最大 300 字選び、ページを 6 倍で描画して1文字ずつ切り出します。埋め込まれていないフォントは、同名のシステムフォントで描画して補います。
  2. 「その他」の字形を集める学習 PDFで使われていないインストール済みフォントから最大 12 書体、各 120 字を描画します。PDFに無い書体を見分けるための反例です。
  3. 劣化させて水増しする学習 1字形につき 2 通り、縮小・ぼかし・ノイズ・JPEG圧縮・太さの変化をかけ、画像内の文字の見え方に近づけます。
  4. 特徴量を計算して学習する学習 1字形を 400 次元のベクトルにし、標準化してロジスティック回帰を学習します。
  5. 画像内の文字を1字ずつ分類する判定 Tesseract で読んだ行を、インクの切れ目で1文字ずつに区切り、各文字のフォントの確率を出します。
  6. 行ごとにまとめて判定する判定 行内の文字の確率を平均し、最も高いフォントの確率が 0.55 以上なら、そのフォントの行とします。
学習データ

クラスは「PDFのフォント」と「その他」

游ゴシック 游ゴシック Bold Century その他のフォント
クラス字形の出どころ条件
PDFのフォント本文 (テキストレイヤー) から切り出し埋め込みフォントのみ。非埋め込みはビューアの代替フォントで描かれるため使わない

その他PDFで使われていないシステムフォントで描画文字種 (和文/欧文) ごとに偏らないよう選ぶ

学習できるのは字形が 20 以上あるフォントだけです。クラスが2つ未満 (PDFのフォントが1種類で、「その他」に使えるフォントも無い場合など) のときは学習せず、字形照合に切り替えます。

字形が同じ別名フォントは「その他」から外す

Windows には、同じ字形を別名で収めたフォントがあります。PDFが MS 明朝を使っているときに MS P明朝を「その他」として学習すると、同じ字形に別のラベルが付き、判定が崩れます。そこで次のフォントは「その他」に入れません。

水増し

本文の字形を、画像の中の文字のように劣化させる

本文の字形は高解像度でくっきりしていますが、画像内の文字は小さく、ぼやけ、圧縮されています。学習時にこの差を埋めるため、1字形ごとに乱数で次の処理をかけます。下の図は、このページ上で「書」の字を実際に処理したものです。

特徴量

形の傾向と、線の太さ

1字形を 400 次元のベクトルにします。形の傾向を表す HOG と、書体の性格を表す線の太さの統計を組み合わせます。

線の太さの特徴 (19 値) は 4 回ずつ繰り返して 76 次元にし、324 次元の HOG に埋もれないよう重みを付けています。

縦画と横画の太さの比が、明朝体を見分ける

明朝体は横画が細く縦画が太いのに対し、ゴシック体はほぼ同じ太さです。インクの連続長 (縦方向の連続 = 横画の太さ、横方向の連続 = 縦画の太さ) の下位 25% 点をとり、その比の対数を特徴量にしています。

連続長の中央値を使うと、横画そのものの長さ (ゴシック体の「書」で 23px) を拾ってしまうため、短い側の代表値を使います。

分類と判定

ロジスティック回帰と、行ごとの平均

項目設定
モデルStandardScaler → LogisticRegression(C=0.01, class_weight="balanced")
クラスの偏り「その他」は字形が多いため、クラスごとの件数で重みを付けて均す
文字種の制約欧文だけを学習したフォント (Century など) は、和文の文字には割り当てない
判定に使う文字OCR の確信度 60 以上。記号・句読点・「一」「ー」「l」など形が書体で変わらない文字は除く
行の判定2 文字以上の確率を平均し、最上位が PDFのフォントで 0.55 以上なら該当

学習と OCR の結果は文書ごとに保存するため、フォントの選択・判定方式・しきい値を変えても再計算しません。

限界

わかっている弱点

  • よく似た書体は区別しにくい。丸ゴシックと角ゴシック、手書き風と明朝のように、骨格が近いものは誤って受け入れます。しきい値を 0.60〜0.65 に上げると除外は増え (72〜85%)、検出は減ります (90〜75%)。
  • 「その他」の書体数に左右される。評価環境では和文の「その他」は数書体でした。Windows 標準の日本語フォントが使える環境では、除外の精度は上がる見込みですが、まだ確認していません。
  • 学習に時間がかかる。評価に使った CPU では、OCR を含めて 1 文書あたり約 50 秒でした。結果は文書ごとに保存されるので、かかるのは初回だけです。
  • 横書きのみ。縦書きの行や、回転したページの本文からは字形を集めません。
  • 評価は合成画像。ベンチマークは描画した文字画像で行いました。実際のスクリーンショットや写真での精度は未評価です。

誤検出が気になるときはしきい値を上げ、見落としが気になるときは下げてください。UI では画像内の各行にマウスを重ねると、両方式の上位候補と確率を確認できます。

使い方

UI と CLI

Web UI で「画像内の文字も判定」をオンにすると、判定方式として機械学習が選ばれた状態になります。字形照合に切り替えると、しきい値は 0.85 に変わります。

python -m font_detector scan input.pdf --font "MS 明朝" --images --method ml -o out.pdf
python -m font_detector scan input.pdf --font "MS 明朝" --images --method ml --min-score 0.65
ファイル役割
mlclassifier.py学習データの収集、水増し、特徴量、学習、行の判定
imagescan.py画像領域の OCR と、字形照合・機械学習の両方式でのスコア計算
glyphs.py本文からの字形の切り出し、システムフォントでの描画
sysfonts.pyインストール済みフォントの一覧と、収録文字の確認
